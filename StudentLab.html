Session 1: Client Discovery & Requirement Gathering

Client Brief: Best Music Entertainment (BME)
BME is launching a new event ticketing and e-commerce platform. They expect high traffic spikes during ticket sales and need a secure, scalable solution on AWS. They are unsure about specific technical requirements and need guidance.
Your Role: Cloud Engineer @ ZICT
Your first task is to conduct a discovery session to gather technical requirements across 9 key domains to inform your architecture design.

Guided Solution: Discovery Questions

Below are the model questions you should ask the client for each domain.

Domain 1: Geographic Location & Availability
  • Q1: Where is your primary customer base located? (Justification: Determines AWS Region for lowest latency)
  • Q2: Do you require failover capabilities if a data center goes down? (Justification: Determines Multi-AZ requirements)
Domain 2: Compute
  • Q1: What is the expected traffic volume during ticket sales vs. normal days? (Justification: Sizing EC2 and Auto Scaling policies)
  • Q2: Is the application monolithic or microservices-based? (Justification: EC2 vs ECS/Lambda decision)
Domain 3: Storage
  • Q1: Do you need to store static assets like event images/videos? (Justification: S3 requirement)
  • Q2: Do these assets need to be publicly accessible or private? (Justification: S3 bucket policies/CloudFront)
Domain 4: Database
  • Q1: Is your data structured (SQL) or unstructured (NoSQL)? (Justification: RDS vs DynamoDB)
  • Q2: How critical is data consistency for ticket sales? (Justification: ACID compliance requirement)
Domain 5: Networking
  • Q1: Do you need a private network for your database? (Justification: VPC Private Subnets)
  • Q2: Do you need a custom domain name (e.g., bme.com)? (Justification: Route 53)
Domain 6: Security
  • Q1: Do you handle credit card or personally identifiable information (PII)? (Justification: Determines PCI-DSS/GDPR compliance and encryption needs — WAF, KMS, Shield)
  • Q2: Do you need protection from DDoS attacks or bot traffic? (Justification: Determines need for AWS WAF and AWS Shield)
Domain 7: IAM — Identity and Access Management
  • Q1: How many developers, admins, and teams need access to your AWS environment? (Justification: Determines IAM users, roles, and groups required)
  • Q2: Do different teams need different levels of access (read-only vs full admin)? (Justification: Determines least-privilege policies)
Domain 8: Monitoring & Compliance
  • Q1: Do you need real-time alerts when your server goes down or CPU spikes? (Justification: CloudWatch alarms + SNS email/SMS alerts)
  • Q2: Do you need an audit log of who accessed or changed what in your environment? (Justification: CloudTrail for compliance logging)
Domain 9: Cost
  • Q1: What is your monthly cloud budget? (Justification: Determines AWS Budgets threshold and alerts)
  • Q2: Do you need to track costs per team, environment, or project? (Justification: Cost allocation tags + Cost Explorer)

Session 5 & 6: Architecture Documentation

Client Brief: BME's executive team needs a written explanation — not just a diagram — of how all the AWS services work together to deliver high availability, performance, and security for their platform.
Your Role: Write professional technical documentation explaining the relationships between AWS services, not just their definitions.
Important: Do not write service definitions. Write how each service relates to and supports the others. Focus on performance, scalability, security, and availability in context of BME's needs.

Model Documentation — Full Answer

Region & Availability Zones

BME's infrastructure is deployed in us-east-1 (N. Virginia) across two Availability Zones: us-east-1a and us-east-1b. This dual-AZ setup ensures that if one data center experiences an outage, all traffic automatically routes to the second AZ — delivering high availability without manual intervention. The region was selected for its proximity to BME's primary customer base and the broadest availability of AWS services.

VPC & Networking

BME's application runs inside a Virtual Private Cloud (VPC) with a CIDR of 10.0.0.0/16. The VPC contains four subnets: two public subnets (hosting the ALB) and two private subnets (hosting EC2 instances and RDS). This separation ensures no external user can directly reach the web servers or database without first passing through the load balancer, which acts as the single controlled entry point. The Internet Gateway allows inbound traffic to reach the public subnets, while the NAT Gateway allows private subnet resources (EC2) to reach the internet for updates without being publicly exposed.

Compute — EC2 & Auto Scaling

BME's web application runs on EC2 t3.medium instances configured with Auto Scaling. During high-traffic events like ticket sales, Auto Scaling automatically launches additional instances to handle demand. When traffic drops, it scales back to prevent unnecessary cost. Each EC2 instance runs Apache as the web server and serves the BME front-end application. The Auto Scaling Group is distributed across both Availability Zones to maintain uptime even if one AZ goes offline.

Load Balancing

The Application Load Balancer (ALB) sits in the public subnets and receives all inbound HTTP/HTTPS traffic. It distributes requests evenly across all healthy EC2 instances in the Auto Scaling Group using round-robin routing. The ALB's health checks ensure traffic is only sent to instances that are running and responding correctly. This prevents a single failing server from degrading the user experience during a live ticket sale event.

Security Layer

Security Groups act as virtual firewalls controlling what traffic can reach each resource. The ALB security group allows only HTTP (80) and HTTPS (443). The EC2 security group allows only traffic from the ALB security group — not from the public internet directly. The RDS security group allows only MySQL traffic (port 3306) from the EC2 security group. AWS WAF is attached to the ALB to block SQL injection, XSS, and common attack patterns. KMS encrypts data at rest for RDS and S3. ACM provides the SSL certificate for HTTPS termination at the ALB.

Storage

Amazon S3 stores BME's event images, marketing assets, and application logs. Versioning is enabled so accidental deletions can be recovered. S3 is not publicly accessible directly — instead, CloudFront distributes content from S3 globally via edge locations, reducing load on the origin server and accelerating content delivery for fans across different locations. EBS volumes provide block storage for each EC2 instance's operating system and local application files.

Database

Amazon RDS for MySQL stores all transactional data: ticket orders, customer accounts, and payment records. RDS runs in Multi-AZ mode, maintaining an automatic standby replica in the second availability zone. If the primary database fails, RDS automatically fails over to the standby — typically within 60–120 seconds — with no data loss. Automated backups are enabled with a 7-day retention period. The database is in a private subnet with no public IP, accessible only from EC2 instances.

Monitoring & Compliance

CloudWatch monitors all resources — CPU, memory, request count, error rate — and triggers SNS alerts to the operations team if thresholds are breached. CloudTrail logs every API action in the AWS account, providing a complete audit trail of who did what and when. This is essential for compliance reporting and incident investigation.

Session 7: Build Network & Web Server

Your Role: Implement the foundational network and first web server for the BME platform.
STEP 1: Create VPC
  1. Go to VPC Dashboard > Create VPC
  2. Select VPC only
  3. Name tag: bme-vpc
  4. IPv4 CIDR: 10.0.0.0/16
  5. Click Create VPC
STEP 2: Create Subnets

Go to Subnets > Create subnet. Select bme-vpc.

  • Subnet 1: Name: bme-public-1a | AZ: us-east-1a | CIDR: 10.0.1.0/24
  • Subnet 2: Name: bme-public-1b | AZ: us-east-1b | CIDR: 10.0.2.0/24
  • Subnet 3: Name: bme-private-1a | AZ: us-east-1a | CIDR: 10.0.3.0/24
  • Subnet 4: Name: bme-private-1b | AZ: us-east-1b | CIDR: 10.0.4.0/24
STEP 3: Internet Gateway & Routes
  1. Create IGW named bme-igw and attach to bme-vpc
  2. Create Route Table named bme-public-rt
  3. Add Route: 0.0.0.0/0 -> Target: bme-igw
  4. Subnet Associations: Edit associations > Select both public subnets > Save
STEP 4: Launch Web Server
  1. Go to EC2 > Launch Instance
  2. Name: bme-web-01
  3. OS: Amazon Linux 2023
  4. Instance Type: t2.micro or t3.micro
  5. Key Pair: Create new bme-key
  6. Network Settings: bme-vpc, bme-public-1a, Auto-assign Public IP: Enable
  7. Security Group: Allow SSH (22) and HTTP (80) from Anywhere
  8. User Data: (Advanced details) 
    #!/bin/bash
yum update -y
yum install httpd -y
systemctl start httpd
systemctl enable httpd
echo "<h1>Welcome to BME Platform - Server 1</h1>" > /var/www/html/index.html
  9. Launch Instance
STEP 5: Create Launch Template & Auto Scaling Group
  1. EC2 > Instances > Select bme-web-01 > Actions > Image and templates > Create template from instance
  2. Name: bme-launch-template
  3. Confirm the User Data script is included (check Advanced details section)
  4. Create launch template
  5. Go to Auto Scaling Groups > Create
  6. Name: bme-asg | Launch Template: bme-launch-template
  7. Network: bme-vpc | Subnets: Select BOTH public subnets
  8. Group size: Desired 2, Minimum 2, Maximum 4
  9. Create Auto Scaling Group
  10. Wait 2–3 minutes. Verify new instances appear in EC2 console.
STEP 6: Verify Everything

Copy the Public IPv4 address of your instance and paste it into a browser tab.

Expected Output: You should see a white page with "Welcome to BME Platform - Server 1".

Verify Auto Scaling: Go to EC2 Instances and confirm 2 instances launched from the template are running.

Session 8: ALB + HTTPS + Auto Scaling

STEP 1: Create Application Load Balancer
  1. EC2 Dashboard > Load Balancers > Create Load Balancer
  2. Select Application Load Balancer
  3. Name: bme-alb | Scheme: Internet-facing
  4. Network: Select bme-vpc and BOTH public subnets (1a & 1b)
  5. Security Group: Create new bme-alb-sg (Allow HTTP 80 & HTTPS 443 from Anywhere)
STEP 2: Create Target Group
  1. Go to Target Groups > Create Target Group
  2. Type: Instances | Name: bme-tg | Protocol: HTTP 80
  3. VPC: bme-vpc
  4. Health Check: Path /
  5. Next > Select your running instance bme-web-01 > Include as pending below > Create
STEP 3: HTTPS Setup (Self-Signed)

Note: Since we don't have a real domain, we use a self-signed cert for testing.

  1. On local terminal (Linux/Mac) or Git Bash: 
    openssl req -x509 -nodes -days 365 -newkey rsa:2048 -keyout bme.key -out bme.crt
  2. Go to AWS ACM (Certificate Manager) > Import Certificate
  3. Paste body of bme.crt into Certificate body
  4. Paste body of bme.key into Private key
  5. Import. Copy the ARN.
  6. Go back to ALB > Listeners > Add Listener > Protocol HTTPS (443) > Default Action: Forward to bme-tg > Select imported certificate.
STEP 4: Configure Auto Scaling with ALB
  1. Go to Auto Scaling Groups > Edit bme-asg (or create new if not done yet)
  2. Under Load Balancing, select: Attach to an existing load balancer
  3. Choose from existing target groups: bme-tg
  4. Health check type: ELB (uses ALB health checks)
  5. Update
  6. Wait 2–3 minutes, then visit the ALB DNS name in browser

Expected Output: You should see the BME web page. Each browser refresh may show a different server IP if you added it to the HTML.

STEP 5: Add HTTP to HTTPS Redirect
  1. ALB > Listeners > Select HTTP:80 listener > Edit
  2. Change default action to: Redirect to HTTPS (443)
  3. Status code: 301 (Permanent)
  4. Save changes
  5. Test: Visit http://[ALB-DNS] — it should redirect to HTTPS automatically
Health Check Warning: If your ALB target group shows targets as Unhealthy, check: (1) EC2 security group allows HTTP from ALB security group, (2) Apache is running on the instance, (3) Health check path / returns HTTP 200.

  4. Create Subscription: Protocol: Email | Endpoint: your email address

  6. Go to CloudWatch > Alarms > Create Alarm
  7. Select metric: EC2 > Per-Instance Metrics > CPUUtilization

  1. Go to CloudTrail Console > Create trail

Part F: CloudFront Distribution
  1. Go to CloudFront Console > Create Distribution
  2. Origin domain: Select your bme-alb DNS name
  3. Protocol: HTTPS only
  4. Viewer protocol policy: Redirect HTTP to HTTPS
  5. Create distribution — wait ~5 minutes for deployment
  6. Copy the CloudFront domain name (e.g., d1abc123.cloudfront.net)
  7. Test in browser — you should see the BME web page

Part 2: First Terraform Deployment

STEP 1: Install & Configure Tools

In AWS CloudShell or on your local machine:

# Install Terraform (Amazon Linux / CloudShell)
sudo yum install -y yum-utils
sudo yum-config-manager --add-repo https://rpm.releases.hashicorp.com/AmazonLinux/hashicorp.repo
sudo yum -y install terraform

# Verify
terraform -version

# Configure AWS CLI (if not done already)
aws configure
# Enter: Access Key ID, Secret Key, us-east-1, json

# Test
aws sts get-caller-identity
STEP 2: Create main.tf

Create folder bme-terraform-intro, then inside create main.tf:

provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "bme_test" {
  ami           = "ami-0c02fb55956c7d316"  # Amazon Linux 2 — us-east-1
  instance_type = "t3.micro"

  tags = {
    Name        = "bme-terraform-test"
    Environment = "UAT"
    Project     = "BME-Platform"
  }
}

output "instance_id" {
  value = aws_instance.bme_test.id
}

output "public_ip" {
  value = aws_instance.bme_test.public_ip
}
STEP 3: Initialize, Plan, Apply, Destroy 
# Initialize — downloads AWS provider
terraform init

# Preview what will be created
terraform plan

# Create the EC2 instance
terraform apply
# Type "yes" when prompted

# Verify: Check AWS Console — EC2 instance "bme-terraform-test" should be running

# Destroy to avoid cost
terraform destroy

STEP 2: Configure GitHub Secrets

  2. Add New Repository Secret:

    • AWS_SECRET_ACCESS_KEY_DEV
STEP 3: Create Workflow File

Create file .github/workflows/terraform-dev.yml:

name: "Terraform Deploy Dev"

on:
  push:
    branches:
      - main
    paths:
      - 'dev/**'

jobs:
  terraform:
    name: "Terraform"
    runs-on: ubuntu-latest
    
    steps:
      - name: Checkout
        uses: actions/checkout@v3

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v2

      - name: Terraform Init
        run: terraform init
        working-directory: ./dev
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID_DEV }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY_DEV }}
          AWS_REGION: "us-east-1"

      - name: Terraform Apply
        run: terraform apply -auto-approve
        working-directory: ./dev
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID_DEV }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY_DEV }}
          AWS_REGION: "us-east-1"
