✅ Guided Solution — Requirement Gathering Answers

Domain 1: Geography

  • Primary Region: us-east-1 (N. Virginia) — closest to majority of BME's customer base and event venues
  • Secondary Region (DR): us-west-2 (Oregon) — for disaster recovery
  • Multi-AZ: Yes — us-east-1a and us-east-1b minimum
  • Justification: High event traffic requires low latency; two AZs ensure availability during single AZ failure

Domain 2: Identity & Access Management (IAM)

  • IAM Roles: Admin, Developer, ReadOnly, DeploymentRole
  • MFA: Required for all human users
  • Principle of Least Privilege: Yes — custom policies per role
  • Service Accounts: EC2 instance roles, ECS task roles, Lambda execution roles

Domain 3: Compute

  • Service: Amazon EC2 (web/app tier), Auto Scaling Group for dynamic scaling
  • Instance Type: t3.medium (dev), t3.large (UAT), c5.xlarge (production web)
  • Containers: Amazon ECS Fargate (final project)
  • Justification: Auto Scaling handles 100k+ peak event traffic automatically

Domain 4: Security

  • WAF: AWS WAF on ALB — block OWASP top 10, rate limiting
  • DDoS: AWS Shield Standard (free tier) on all public endpoints
  • Encryption: KMS for S3, RDS, EBS — all at rest
  • SSL/TLS: ACM certificates on ALB — HTTPS only in production
  • Threat Detection: Amazon GuardDuty enabled on all accounts
  • Secrets: AWS Secrets Manager for DB credentials and API keys

Domain 5: Storage

  • Object Storage: Amazon S3 — media files, static assets, Terraform state, logs
  • Block Storage: Amazon EBS gp3 — attached to EC2 instances
  • Versioning: S3 versioning enabled on all buckets
  • Lifecycle: S3 lifecycle rules — move to Glacier after 90 days

Domain 6: Networking

  • VPC: Custom VPC per environment (10.0.0.0/16 dev, 10.1.0.0/16 UAT, 10.2.0.0/16 prod)
  • Subnets: Public (web), Private App, Private DB — in each AZ
  • Internet Gateway: For public subnets
  • NAT Gateway: For private subnets to access internet
  • ALB: Internet-facing Application Load Balancer
  • Route 53: DNS management, health checks, failover routing
  • CloudFront: CDN for static assets and ticket pages

Domain 7: Database

  • Service: Amazon RDS MySQL Multi-AZ
  • Engine: MySQL 8.0
  • Instance: db.t3.medium (dev/UAT), db.r5.large (production)
  • Backup: Automated daily backups, 7-day retention
  • Read Replica: Production environment — 1 read replica for reporting

Domain 8: Monitoring & Alerting

  • CloudWatch: Metrics, alarms, dashboards for EC2, ALB, RDS, Lambda
  • CloudTrail: API audit logging — all regions, all accounts
  • SNS: Alert notifications to engineering team email
  • Config: AWS Config for compliance monitoring

Domain 9: Cost Management

  • AWS Budgets: Monthly budget alerts at 80% and 100% threshold
  • Cost Explorer: Weekly review by ZICT project lead
  • Reserved Instances: Production EC2 and RDS — 1-year term after 3 months
  • Auto Scaling: Scale down during off-peak hours (2am–6am)

Assessment 4 — Architecture Documentation
Written Technical Documentation for the Development Architecture
📋 Client Scenario — Project Ticket

"ZICT-TICKET-004: The board loved the diagram. Now we need the supporting technical write-up. Please document how each service in the Development diagram contributes to performance, scalability, and security. This goes into our client-facing technical brief."

✅ Guided Solution — Architecture Documentation Template

Section 1: Executive Summary

The BME Development environment is hosted on AWS in the us-east-1 region using a multi-AZ architecture. It is designed to validate application code in a cost-efficient environment that mirrors the production topology while using smaller instance sizes. The environment uses a three-tier model (web, application, database) with full network isolation via a custom VPC.

Section 2: Network Layer

  • VPC (10.0.0.0/16): Provides complete network isolation for the BME development workload
  • Public Subnets: Host the ALB and NAT Gateways — no application logic exposed directly
  • Private Subnets: Host EC2 (app) and RDS (db) — inaccessible from internet
  • Route Tables: Public routes to IGW; Private routes to NAT Gateway

Section 3: Compute & Scaling

  • EC2 (t3.medium): Runs the BME web application — cost-appropriate for development
  • Auto Scaling Group: Maintains at least 1 instance; scales to 3 during peak test loads
  • ALB: Routes HTTP/HTTPS traffic to healthy EC2 instances; enables path-based routing

Section 4: Data Layer

  • RDS MySQL: Managed relational database for BME ticketing data — dev uses single-AZ to reduce cost
  • EBS gp3: High-performance block storage attached to EC2 instances
  • S3: Stores static assets, media files, and Terraform state

Section 5: Security Layer

  • IAM Roles: EC2 instance profile with least-privilege S3 and CloudWatch access
  • Security Groups: ALB SG (80, 443 inbound); EC2 SG (80 from ALB only); RDS SG (3306 from EC2 only)
  • ACM: SSL certificate for HTTPS on ALB
  • KMS: Server-side encryption on S3 and RDS

Section 6: Monitoring

  • CloudWatch: EC2 CPU, memory, network alarms; RDS connection count and storage
  • CloudTrail: All API calls logged to S3 bucket for audit trail
  • SNS: Email alerts when CloudWatch alarms trigger

Assessment 7 — VPC, Subnets, EC2 & Apache Setup
Build BME's Development Network Infrastructure in AWS Console
📧 Client Scenario

"Time to build. Start with the network layer for Development. Create the VPC, subnets, IGW, route tables, and launch one EC2 instance running Apache to confirm the web server is reachable."

✅ Guided Solution — Step by Step

Step 1: Create VPC

  1. Go to AWS Console → VPC → Your VPCs → Create VPC
  2. Name tag: BME-Dev-VPC
  3. IPv4 CIDR: 10.0.0.0/16
  4. Click Create VPC

Step 2: Create Subnets

  1. VPC → Subnets → Create Subnet → select BME-Dev-VPC
  2. Public Subnet 1a: Name BME-Dev-Public-1a, AZ us-east-1a, CIDR 10.0.1.0/24
  3. Public Subnet 1b: Name BME-Dev-Public-1b, AZ us-east-1b, CIDR 10.0.2.0/24
  4. Private App 1a: Name BME-Dev-Private-App-1a, AZ us-east-1a, CIDR 10.0.3.0/24
  5. Private App 1b: Name BME-Dev-Private-App-1b, AZ us-east-1b, CIDR 10.0.4.0/24
  6. Private DB 1a: Name BME-Dev-Private-DB-1a, AZ us-east-1a, CIDR 10.0.5.0/24
  7. Private DB 1b: Name BME-Dev-Private-DB-1b, AZ us-east-1b, CIDR 10.0.6.0/24

Step 3: Internet Gateway

  1. VPC → Internet Gateways → Create IGW → Name: BME-Dev-IGW
  2. Select IGW → Actions → Attach to VPC → select BME-Dev-VPC

Step 4: Route Tables

  1. VPC → Route Tables → Create Route Table → Name: BME-Dev-Public-RT → VPC: BME-Dev-VPC
  2. Edit Routes → Add Route: Destination 0.0.0.0/0, Target: BME-Dev-IGW
  3. Subnet Associations → Edit → associate both Public subnets
  4. Create another RT: BME-Dev-Private-RT → VPC: BME-Dev-VPC
  5. Associate BME-Dev-Private-RT with Private-App-1a, Private-App-1b, Private-DB-1a, and Private-DB-1b

Step 5: Create Elastic IP and NAT Gateway

  1. VPC → Elastic IPs → Allocate Elastic IP address
  2. VPC → NAT Gateways → Create NAT Gateway
  3. Name: BME-Dev-NAT-1a · Subnet: BME-Dev-Public-1a
  4. Attach the newly allocated Elastic IP
  5. Create NAT Gateway → wait until status shows Available

Step 6: Update Private Route Table for NAT Egress

  1. Open BME-Dev-Private-RT → Edit Routes
  2. Add route: Destination 0.0.0.0/0 → Target: BME-Dev-NAT-1a
  3. Save changes and verify private subnets now have outbound internet access through the NAT Gateway

Step 7: Security Group for EC2

  1. EC2 → Security Groups → Create → Name: BME-Dev-EC2-SG, VPC: BME-Dev-VPC
  2. Inbound Rules: SSH (22) from My IP; HTTP (80) from Anywhere (0.0.0.0/0)
  3. Outbound: All traffic — Anywhere

Step 8: Launch Public Validation EC2 and Install Apache

  1. EC2 → Launch Instance → Name: BME-Dev-Web-01
  2. AMI: Amazon Linux 2023 · Instance type: t2.micro
  3. Key Pair: create or select existing
  4. Network: BME-Dev-VPC · Subnet: BME-Dev-Public-1a · Enable Auto-assign Public IP
  5. Security Group: BME-Dev-EC2-SG
  6. User Data (paste this):
#!/bin/bash
yum update -y
yum install -y httpd

💼 Week 3 Interview Questions
  • What is CloudTrail used for, and how is it different from CloudWatch?
    CloudTrail records AWS API activity for governance and audit, while CloudWatch focuses on metrics, logs, alarms, and operational monitoring.
  • How does an SNS topic connect to a CloudWatch alarm in a monitoring workflow?
    CloudWatch detects a threshold breach, the alarm changes state, and the alarm action publishes to an SNS topic which then sends email or other notifications.
  • Why would you move from manual AWS Console work to Terraform?
    Terraform makes infrastructure repeatable, version-controlled, easier to review, and much faster to promote across Dev, UAT, and Prod.
  • What changes when promoting Terraform from Dev to UAT to Prod?
    Environment values change such as CIDR blocks, instance sizes, database sizing, cost level, and high-availability settings like Multi-AZ.
  • Why are AWS Budgets and alerts important in a training or lab environment?
    They help control spend early and show employers that you understand cost governance, not just deployment.

WHAT IS TERRAFORM?

Terraform Definition

Infrastructure as Code (IaC) - Write code to create AWS resources

Instead of clicking AWS Console:

❌ Manual (BAD):
  → Click AWS Console
  → Create VPC
  → Create EC2
  → Create RDS
  → (Takes hours, easy to miss steps)

✅ Terraform (GOOD):
  → Write code
  → Run terraform apply
  → Everything created automatically
  → (Takes minutes, reproducible)
Why Terraform?
  • Automation: One command creates everything
  • Reproducible: Same code = same infrastructure every time
  • Version Control: Track infrastructure changes like code
  • Reusable: Copy code to Dev/UAT/Prod, change variables only
  • Teamwork: Share infrastructure as code with team

name: BME Terraform CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  AWS_REGION: us-east-1
  TF_VERSION: 1.7.0

jobs:
  terraform-plan:
    name: Terraform Plan
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: environments/dev
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ${{ env.AWS_REGION }}
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}
      - name: Terraform Init
        run: terraform init
      - name: Terraform Validate
        run: terraform validate
      - name: Terraform Plan
        run: terraform plan -no-color

  terraform-apply:
    name: Terraform Apply
    runs-on: ubuntu-latest
    needs: terraform-plan
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    defaults:
      run:
        working-directory: environments/dev
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ${{ env.AWS_REGION }}
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}
      - name: Terraform Init
        run: terraform init
      - name: Terraform Apply
        run: terraform apply -auto-approve
